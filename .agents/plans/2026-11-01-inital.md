# Convo 
I'd build this as a personal recipe library that gradually evolves into a smart meal planner.

Since your existing workflow is finding recipes in Markdown, I wouldn't start with a complicated meal-planning system. I'd prioritize making recipes incredibly easy to save, organize, find, and cook.

The key is designing V1 so that your future pantry inventory and AI recipe generation features fit naturally without requiring a rewrite.

## 3. Design your Markdown format for future features

This is probably the most important architectural decision.

I'd use Markdown with YAML frontmatter, similar to Obsidian. That keeps recipes human-readable and portable while giving your application structured metadata.

```

---
id: kimchi-fried-rice
title: Kimchi Fried Rice
tags:
  - korean
  - quick
  - dinner
  - rice
servings: 2
prepMinutes: 5
cookMinutes: 15
favorite: true
ingredients:
  - name: cooked rice
    quantity: 2
    unit: cup
  - name: kimchi
    quantity: 1
    unit: cup
  - name: sesame oil
    quantity: 1
    unit: tbsp
  - name: egg
    quantity: 2
    unit: whole
---

# Kimchi Fried Rice

## Instructions

1. Heat sesame oil in a pan.
2. Add kimchi and stir-fry.
3. Add cooked rice and mix.
4. Top with fried eggs.

## Notes

- Day-old rice works best.
- Add gochujang for extra spice.

```

Why this format works:

- V1: Tags, search, favorites, ingredients, and cooking instructions.
- V1.5: Ingredient quantities can generate shopping lists and scale servings.
- V2: Your pantry can match normalized ingredients against saved recipes.
- V3: AI can recommend substitutions and generate recipes using your inventory.

One important detail: store ingredients as structured data, not only as free-form Markdown strings. Otherwise, matching "2 tbsp olive oil" against "olive oil" in your pantry becomes unnecessarily difficult.

## 5. Next.js architecture

Given your TypeScript experience, I'd use a straightforward stack:

| Layer    | Recommendation                                |
| -------- | --------------------------------------------- |
| Frontend | Next.js App Router + TypeScript               |
| UI       | Tailwind CSS + shadcn/ui                      |
| Database | SQLite locally, PostgreSQL when deployed      |
| ORM      | Drizzle                                       |
| Markdown | `react-markdown`, `remark-gfm`, `gray-matter` |
| Search   | Database filtering initially                  |
| Images   | Local files or S3/R2 later                    |
| AI (V2)  | Ollama locally or an API-based model          |

For a single-user local application, you could even skip the database initially and store recipes as `.md` files in a directory. However, if you expect to add authentication, synchronization, and inventory tracking, I'd start with a database and support Markdown import/export.

### Future-proof data model

Conceptual relationships. Tags and recipe-tag joins are omitted for clarity.

The shared `Ingredient` table is the bridge between your recipe library and future pantry.

For example, "scallions", "green onions", and "spring onions" should resolve to the same canonical ingredient where appropriate.

| Phase | Scope                                  | Estimated solo development |
| ----- | -------------------------------------- | -------------------------- |
| V1.0  | Markdown CRUD, tags, search, favorites | 2–4 days                   |
| V1.1  | Cooking view, checklists, notes        | 1–2 days                   |
| V1.2  | Meal planning, shopping lists          | 2–4 days                   |
| V2.0  | Pantry and ingredient matching         | 3–5 days                   |
| V2.1  | AI suggestions and substitutions       | 3–5 days                   |

These are rough estimates assuming AI-assisted development, no complex authentication, and a personal-use application.

My suggested first milestone: Import 10 existing Markdown recipes, organize them with tags, and retrieve one in under 10 seconds. If that workflow feels great, you already have a useful product.

One architectural question before implementing: Do you want your Markdown files to remain the source of truth (like Obsidian, with Next.js as a viewer/editor), or are you comfortable importing them into a database and managing recipes through the app?

That decision determines whether I'd start with a filesystem-based design or Drizzle + SQLite.

# Plan
# dtp-soma Agent-Skill-Based Implementation Plan

## Summary

Use the Sites workflow to build and publish `dtp-soma` as a private, responsive recipe-library Site. V1 includes recipe CRUD, Markdown import/export, structured ingredients, search, tags, favorites, cooking mode, and notes.

The plan keeps MongoDB Atlas as the source of truth, but introduces a small Node-compatible API adapter because Sites-hosted Worker code cannot use raw TCP connections, and MongoDB’s Atlas Data API/HTTPS Endpoints reached end-of-life on September 30, 2025. MongoDB recommends using a native driver with a separate application runtime instead. [MongoDB deprecation guidance](https://www.mongodb.com/docs/data-api-deprecation/)

## Architecture

- Sites frontend:
  - Use the supplied Vinext starter and Sites project workflow.
  - Build the responsive Library, Recipe Detail, and Add/Edit experiences.
  - Keep Site metadata in `.openai/hosting.json`.
  - Start private by default and preserve private audience settings.
- MongoDB API adapter:
  - Add a separate Node-compatible service boundary using the official MongoDB driver.
  - Expose only the required recipe operations: list/search, get, create, update, favorite, mark-cooked, export, and delete.
  - Keep the Atlas connection string server-side.
  - Configure the Site with the adapter’s base URL and a private service credential through native Sites secret configuration.
- Do not use Atlas Data API, browser-side MongoDB access, or a MongoDB connection string in Site/client code.
- Keep the adapter isolated so it can later be deployed alongside the app or moved to another Node runtime without changing the UI contract.

## Data and behavior

Use a recipe document containing:

- Stable ID/slug, title, description, tags, categories, and optional image reference.
- Prep, cook, and total duration.
- Base servings.
- Structured ingredients with display name, canonical name, quantity, unit, and preparation note.
- Original Markdown source.
- Parsed instructions and notes where available.
- Favorite flag, created/updated timestamps, and last-cooked timestamp.

Implement:

- Library cards/list with search, tag/category filters, favorites, and sorting.
- Recipe detail with rendered Markdown, ingredient checklist, serving scaling, cooking mode, notes, favorite toggle, and mark-cooked action.
- Add/edit flow supporting Markdown paste, `.md` upload, structured editing, validation, preview, save, export, and delete.
- YAML frontmatter parsing at the import boundary.
- Conservative ingredient canonicalization stored for future pantry matching.
- Empty, loading, validation-error, API-error, and unavailable-database states.

## Sites workflow and validation

- Create or use the local Site checkout according to the Sites skill.
- Run the supplied project setup and dependency installer.
- Read the applicable preview guidance before browser QA.
- Implement the first recognizable UI, preview it, and verify responsive behavior with `cua_repl` when available.
- Package the Site with the Sites source helper and run the framework build/check command.
- Configure secrets only through Sites-native secret handling; keep `.env.example` limited to variable names.
- Publish privately after source, build, and API integration checks pass.

## Test plan

- Recipe create, edit, favorite, mark-cooked, export, and delete.
- Markdown import with valid frontmatter and structured ingredients.
- Helpful rejection of malformed frontmatter, missing title, invalid servings, and invalid quantities.
- Search by title, tag, category, and ingredient.
- Serving scaling without corrupting textual quantities.
- Cooking checklist behavior without mutating the saved recipe.
- Markdown round-trip import/export.
- API authorization and rejection of missing/invalid service credentials.
- MongoDB connection failure and empty-database handling.
- Responsive and keyboard-accessibility checks for filters, forms, checklists, and cooking mode.
- Site build and deployment verification.

## Assumptions

- V1 remains single-user in practice and has no application-level authentication.
- The Site is private and relies on the Site access boundary plus API service credentials.
- Pantry inventory, shopping lists, meal planning, AI generation, sharing, and multi-user ownership are deferred.
- If the deployment environment cannot host the Node API adapter, the fallback is to run the full Next.js app in a Node-compatible host instead of forcing MongoDB access into the Sites Worker runtime.
